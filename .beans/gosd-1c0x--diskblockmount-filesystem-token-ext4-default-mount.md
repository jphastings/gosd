## Summary of Changes

**disk/disk.go**: `Filesystem` gains `EXT4` alongside `FAT32`/`ExFAT`; `Options.filesystem()`'s zero-value mapping flips from FAT32 to EXT4 (`TestOptionsZeroValueIsTheEXT4Default` replaces the old FAT32-default test) — the epic's locked, deliberate breaking default. Package doc, `FormatAndMount`/`FormatAndMountWith`/`Options` docstrings rewritten to state the flip, that FAT32/exFAT remain for removable-media interop, and that a label match against a *different* filesystem no longer silently mounts as whatever's there (see below). `emmc/` untouched — it always calls `blockmount.Run` with `diskfmt.FAT32` against FAT32-only devices, so every ext4 code path is structurally unreachable from it; `go test ./emmc/...` passes with zero changes to `emmc/*.go`.

**internal/blockmount**: `Run`'s adoption switch now requires the existing volume's filesystem to match the requested one, not just its label — a mismatch (e.g. a drive that arrived exFAT-formatted under the app's label) is now treated like any other foreign content (`reformat iff Destructive, else an actionable error naming both filesystems and the flag`), replacing the old "mount it as whatever it already is" behavior. `ValidateLabel` gained an `fs diskfmt.FS` parameter: FAT32/exFAT keep their existing 11-byte/round-trip rules unchanged; ext4 gets its own 16-byte cap (`ext4LabelBytes`) with none of FAT's edge-space/byte-7 hazards (ext4's `s_volume_name` is NUL-padded, not space-padded, and isn't split into two fields). `remedyFor` gained an ext4-specific branch naming the Pi-family CONFIG_EXT4_FS gap and the Rockchip-fleet+Cubie-A5E boards that have it, pointing at COMPATIBILITY.md (confirmed against every board's recorded `kernel.config`: pi-3b/pi-zero-2w/pi-zero-w all show `# CONFIG_EXT4_FS is not set`; radxa-zero-3e/nanopi-zero2/rock-4se/cubie-a5e/qemu-virt all show `CONFIG_EXT4_FS=y`).

A new `runEXT4` (called from `Run` when `fs == diskfmt.EXT4`) implements the establishment/adoption state machine via five new `Deps` fields (`SyncDevice`, `Grow`, `EstablishMarker`, `MarkerEstablished`, `RootHasOtherContent`, plus reuse of the existing `Unmount`) — all nil-safe for every non-ext4 caller (emmc, and any disk call that never asks for ext4), so the addition is structurally additive. `internal/blockmount/platform_linux.go` implements the real Linux side: `GrowEXT4` (BLKGETSIZE64 read into a `uint64` buffer, never `unix.IoctlGetInt`'s machine-word buffer, which is the exact gosd-fjio 32-bit-ARM truncation bug; converts to a block count via the *mounted* filesystem's own `statfs` block size, not a hardcoded 4KiB), `SyncDevice` (mirrors `dataexpand.syncDevice`), `EstablishEXT4Marker` (writes the marker, fsyncs the file, then fsyncs the parent directory — both matter, neither substitutes for the other), `EXT4MarkerEstablished`, and `RootHasOtherContent` (see Adversarial review notes). `EXT4_IOC_RESIZE_FS`'s ioctl number is computed from `asm-generic/ioctl.h`'s `_IOC()` layout, mirroring `examples/spiloopback`'s existing `SPI_IOC_MESSAGE` derivation, since `golang.org/x/sys/unix` only wraps generic syscalls.

**Crash-safe establishment sequence** (`runEXT4`, fresh-format tail): `Format` (golden image + label/UUID to the raw device) → `SyncDevice` (fsync the raw device node — durable before Mount trusts it) → `Mount` → `Grow` (`EXT4_IOC_RESIZE_FS`, itself ending in a `syncfs(2)` — see below) → `EstablishMarker` (write + fsync file + fsync parent dir). A crash before the marker leaves debris (recognizable superblock, matching label, no marker) that self-heals on the next boot by repeating the whole sequence, including the grow even if it had already run once — the grow left no durable trace a future boot could trust either way, so redoing it costs time, never correctness. Adoption (`format=false`, i.e. label+filesystem already match): mount, then check the marker — present → done, no grow, no reformat (growth happens exactly once, at establishment); absent → treated as crash debris (see below) → unmount → re-run the full establishment sequence from `Format`.

Quality gates: `go test ./...`, `go vet ./...`, `gofmt -l .`, `golangci-lint run ./...` and `GOOS=linux golangci-lint run ./...` all clean. Also spot-checked `GOOS=linux GOARCH=arm64 go build ./...` and `GOOS=linux GOARCH=arm go build` on every touched package (pi-zero-w's 32-bit target, directly relevant given the BLKGETSIZE64 sizing bug this bean specifically guards against).

## Adversarial review notes

Checked against every failure mode CLAUDE.md names, plus a genuine second pass looking for others:

- **Probe-only gates**: adoption requires a real, successful `Mount` (the kernel actually interpreting the filesystem) *and* a marker read through that mount — never just Inspect's superblock probe. A superblock that merely parses (the gosd-lirl scenario, generalized past FAT32 to ext4) is never treated as proof.
- **Marker written before data is durable**: traced the full call chain — Format→SyncDevice happens before the *first* Mount ever trusts the golden image; EstablishMarker is unconditionally the last call, after Grow succeeds.
- **Grow's own durability was originally implicit, not explicit — fixed.** `EXT4_IOC_RESIZE_FS` is a journaled metadata operation; JBD2 commits transactions in strict order, so `EstablishMarker`'s later fsync would, in practice, also force the grow's transaction to commit — but that's an ext4-internals detail, not a contract this package should silently lean on. Added an explicit `unix.Syncfs` call inside `GrowEXT4` itself, so `Grow`'s own postcondition ("returns nil ⇒ durable") is self-contained regardless of what any later step does.
- **fsync of the file but not the parent directory**: `EstablishEXT4Marker` does both explicitly, documented why neither substitutes for the other (ext4 doesn't guarantee a new directory entry is durable just because the file it names is).
- **Partition-size assumptions**: `GrowEXT4` reads the target size fresh via `BLKGETSIZE64` on every call, converted to blocks via the *mounted* filesystem's own `statfs` block size — nothing cached or hardcoded (guards the exact class of bug gosd-fjio was: a stale/truncated size assumption).
- **emmc semantic drift**: `emmc/*.go` untouched; its tests pass unmodified; every new Deps field and the `runEXT4` branch are structurally unreachable from it (it only ever requests `diskfmt.FAT32` against FAT32-only devices, so the new fs-mismatch rule never fires for it either — the only device it would ever see already carries FAT32 when it carries anything).
- **A gap the literal bean text didn't cover, found and fixed**: `EXT4EstablishedMarker` is a plain file *inside* the filesystem it gates, unlike `dataexpand`'s MBR-partition-table entry, which nothing running on that partition can ever reach or delete. As originally built, an app that removed the marker (a "clear my hidden files too" cleanup bug, or anything else) would make an otherwise fully established, data-bearing volume look byte-for-byte identical to fresh crash debris on the very next boot — reformatting it away with no consent, no warning, and no way back. There's no whole-device analog of dataexpand's MBR entry to fall back on (disk formats the whole device, no partition table). Fixed by adding `RootHasOtherContent` as a second opinion, consulted only when the marker is absent: a root directory holding nothing beyond what the golden image itself ships with (`lost+found`) is exactly what an interrupted establishment leaves (an app can only write here *after* `Run` has handed the mountpoint back, which never happened this run) and still self-heals with no consent needed; a root directory with anything else in it now gets the same `destructive`-gated treatment as any other foreign content instead of a silent wipe. New tests: `TestRunEXT4NoMarkerButRealContentRefusesWithoutDestructive`/`...ReformatsWhenDestructive`/`TestRunEXT4RootContentCheckErrorSurfaces`. One residual, documented gap: if `Mount` itself fails outright (rather than succeeding with an empty or non-empty root), there is no way to read the root directory to apply this second opinion, so that path stays an unconditional reformat — accepted rather than fixed here since distinguishing "corrupt debris" from "corrupt-but-real data" with an unmountable filesystem is a materially harder problem or unrelated hardware fault; flagged in `runEXT4`'s doc comment for whoever picks it up next if it ever proves wrong in practice.
- **Concurrency**: `runEXT4`'s entire tentative-mount/check/unmount/reformat dance runs inside the *same* `runMu` critical section `Run` already holds (unchanged), so the existing gosd-45bv proof (two sibling `Run` calls can never both format the same device) structurally covers ext4 too; the `MountedSources` re-check immediately before the destructive `Format` call is preserved at the same point in the sequence.
