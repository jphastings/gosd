Follow-up to gosd-hcyn: resume interrupted image downloads on the File System Access tier. Design sketch (from the gosd-hcyn planning): HTTP Range + If-Range (ETag or Last-Modified) against the image URL; persist the FileSystemFileHandle + progress state in IndexedDB; on resume, re-verify the partial file on disk by re-hashing it with pristine placeholder range bytes swapped back in (store those ~KiB-scale pristine bytes during the first attempt), then continue the stream from the verified offset. The SaveSink interface was deliberately kept sequential-only — add an optional seekable capability rather than changing the base contract. The vendored Sha256 already exposes clone() for in-session checkpoints; cross-session resume needs either serializable hash state or the re-hash approach above (prefer re-hash: no serialization format to maintain). A server 200 (ignoring Range) restarts from scratch.



## Summary of Changes

- **sinks/types.ts**: added `SeekableSaveSink` (extends `SaveSink` with `readExisting()` and an opaque `resumeHandle`) and `isSeekable` — the optional capability the bean asked for, without touching the base sequential-only `SaveSink` contract.
- **sinks/fs-access.ts**: `createFsAccessSink` now returns a `SeekableSaveSink` (backward compatible); added `openPersistedFsAccessHandle`, which re-requests the (session-scoped) readwrite permission on a persisted handle once, reads back the bytes already on disk, and offers `resumeWritingAt(offset)` (`createWritable({keepExistingData:true})` + `.seek(offset)`) and `restartWriting()` (fresh overwrite) for the 200-fallback case.
- **substitute.ts**: refactored the transform's per-chunk logic into a small reusable engine so a new `primeSubstitutionState(manifest, padded, prefix)` can replay an already-downloaded (pristine-reconstructed) prefix through the *exact* same verification/hashing code path a live download uses, producing a `SubstitutionState` that `createSubstitutionTransform`'s new optional `resumeFrom` parameter continues from — this is the bean's "prefer re-hash, no serialization format" choice for the vendored Sha256 (which still only exposes `clone()` for in-session checkpoints). Also added `onPlaceholderVerified`, firing with a patched placeholder's pristine bytes the instant it verifies.
- **preconditions.ts**: `checkImageResponse` gained `expectedContentLength` (defaults to `manifest.image.size`) so a resumed `206`'s Content-Length (the remaining bytes, not the whole image) is checked correctly.
- **run.ts**: `runDownload` gained `resumeFrom` and an optional `checkpoint: DownloadCheckpoint` (onResponseHeaders/onPlaceholderVerified/onFinalized/isUntrustworthy). With a checkpoint set, a failure the checkpoint doesn't classify as untrustworthy (default: anything except the substitution transform's own placeholder/hash/size verification errors) commits (preserving durably-streamed bytes) instead of aborting — necessary because Chromium's fs-access writable only publishes to the real path on close(), so a resume is only ever as good as the last point this code explicitly closed it. Fully backward compatible: omitting `checkpoint` reproduces the exact prior abort-always behaviour (pinned by the existing run.test.ts suite, unchanged).
- **resume-store.ts** (new): a minimal promise-wrapped IndexedDB `ResumeStore` (get/put/delete/list), keyed by `manifest.image.sha256` — a `FileSystemFileHandle` is structured-clonable so it's stored as-is, no serialization format needed. `resumeStoreAvailable`/`createIndexedDbResumeStore` mirror `fsAccessAvailable`'s `target`-injection pattern for testability.
- **resume.ts** (new): the orchestration. `clampToSafeResumeOffset` rolls a resume offset back to a straddled, not-yet-fully-captured patched placeholder's range start (reconstruction is only possible once a placeholder's pristine bytes were fully captured); `reconstructPristinePrefix` swaps captured pristine bytes back into the on-disk prefix before re-hashing. `createFreshDownloadCheckpoint` wires a fresh `withPlaceholders({resumable:true})` fs-access download up to a ResumeStore. `resumeDownload`/`listResumableDownloads`/`discardResumableDownload` are the new public resume entry points: `resumeDownload` re-verifies the partial file, sends `Range`+`If-Range` (ETag or Last-Modified), and either continues from the verified offset (206) or restarts from scratch reusing the same already-picked file (a 200 that ignored Range, or a non-206/200 status throws `GosdImageFetchError`).
- **index.ts**: `withPlaceholders` gained opt-in `resumable`/`resumeStore` options (default off — resuming needs IndexedDB writes callers may not want), wired only into the fs-access tier; re-exports the new public surface.
- Resuming is deliberately NOT wired into `withPlaceholders`'s auto-flow itself (no auto-resume-on-call): the fs-access picker must stay the very first `await`-free call for the click-gesture requirement, which rules out an async IndexedDB lookup beforehand — so an app calls `listResumableDownloads()`/`resumeDownload()` explicitly (e.g. from its own "resume previous download?" prompt), documented in the README's rewritten "Resuming" section.
- New tests: sinks/types.test.ts, resume-store.test.ts, resume.test.ts (clamp/reconstruct unit tests plus full interrupted-then-resumed and 200-fallback round trips against an in-memory fake FileSystemFileHandle), plus additions to substitute.test.ts, run.test.ts, preconditions.test.ts, sinks/fs-access.test.ts and index.test.ts.
- All js gates green: `pnpm install --frozen-lockfile`, `format:check`, `lint`, `typecheck`, `build`, `test` (174 unit tests), `test:integration`. No Go files changed; Go gates (`go test ./...`, `go vet ./...`, `gofmt -l .`, `golangci-lint run ./...` both OSes) run clean.
